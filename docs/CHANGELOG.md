## 2026-10-23 —— 调色板上限 8 → 16 个颜色

**动机**（用户原话）：「同时调色板里的颜色上限定位16种，现在的8种有点少了。」

**根因**：`PAL_MAX = 8` 硬编码在 core 里，`+` 按钮、`effPalette()` / `normalizeEffect()` 的截断、UI 提示与帮助页全跟着它走；`+` 的候选色也只有 8 个（第 9 个起会重复），而导出的 `pal_count` 是 8 位数、`led_gen_palette[]` 是扁平表 —— **16 个在固件侧本来就放得下**，卡住的只是工具侧这道上限。

**改动**：`led_layout_editor.html` —— `PAL_MAX` 8 → 16（`effPalette` / `normalizeEffect` / `rowFromEffect` 落到导出都是它）；`palAddColor()` 的候选色表从 8 个补到 16 个互不相同（白 / 青 / 黄 / 品红 / 绿 / 蓝 / 橙 / 紫 / 红 / 黄绿 / 天蓝 / 玫红 / 琥珀 / 青绿 / 靛 / 粉）；`+` 按钮 tooltip、帮助页「调色板」行、配色注释一律 8 → 16。C 结构体与导出格式**一列都没动**（`pal_count` 本来就是 `uint8_t`）。

**测试**：`test_effects_core` 122 → 124（给 20 个色只留 16、`normalizeEffect` 同一个上限）、`test_fx_presets` 80 → 81（一路点 `+` 到 16 个，第 17 次只弹「调色板最多 16 个颜色」、个数不再涨）；全量 **24 套件 / 1443 项 / 0 FAIL**。

**影响**：老存档（≤8 色）逐字节不变；导出只是可能多几行 `led_gen_palette`，固件无需改动。

**动机**（用户原话）：「这个跳变配色看起来有点怪怪的，感觉亮的时候就是一瞬间，大部分时间都是在变暗。增加两个设置变量吧，一个是亮的时长，一个是变暗速度。」随后又问「点亮是直接从 0 到 255，还是有个缓慢变亮的过程？」—— 想把点亮也做成可调；做完再问「在切换颜色时为啥会有抖一下的感觉」。

**根因**：`stepEnv` 把停留切成「前 1/8 快速点亮 + 其余全程渐灭」—— 亮段最长只有 1/8 停留；上一版把亮段改成满亮之后，启亮仍是 0 → 255 一拍照跳（20ms 一拍），没有渐变可调。**「抖一下」**（用户补一句：「渐变色里面，从一种颜色变暗切换到下一颜色时，会出现抖一下」）= 两处叠加：① 渐亮第 0 拍恒为 0，接在上一色「变暗」最后一拍（也是 0）后面，换色处**连黑 2 拍**（40ms），4 拍渐亮里能看到的只有 3 级（85 / 170 / 255）；② 变暗最后一拍落到 **0** —— 20ms 全黑一帧在 50Hz 下就是一次闪，紧跟着又跳回 63/127，看着就是换色处一顿一抖。

**改动**：包络换成四段 —— `r` 拍 `255/r → 255` 匀速渐亮（「渐亮(拍)」，`r = 0` 即硬启亮、逐拍与上一版相同；第 1 拍不是 0 —— 换色处不许有全黑帧，否则会连黑两拍、看着发顿）→ 满亮 `h` 拍（「亮(拍)」）→ `f` 拍匀速暗下去、最后一拍停在 ≈`255/(f+1)`（「变暗(拍)」，**不落 0**：全黑一帧在 50Hz 下就是一次闪，换色处会「抖一下」）→ 就在这一拍换下一种；`r + h + f` 之外不再留黑拍：**「停留(拍)」= 渐亮 + 亮 + 变暗，填这三行时自动算好填回那一格**（`stepSpeedOf`，那一格只读；上限 255 拍，超了状态栏说明实际按 渐亮 / 亮 / 暗 多少播）。`stepClamp(d, r, h, f)` / `stepEnv(t, d, r, h, f)` / `led_gen_step_env()` 逐值相同；效果多三个字段 `rise` / `hold` / `fade`（导出的 `led_gen_effect_t` 末尾是 `step_rise` / `step_hold` / `step_fade` 三列，`rowFromEffect` / `CORE.effectPreset` / `instApplyPreset` 全程带着走，实例周期也按三段之和定）。缺省：`rise` = 0（老存档 / 老预置打开即得，逐拍不变）、`hold` = 停留一半、`fade` = 停留 − 渐亮 − 亮。UI 在「停留(拍)」下多三行（只在跳变时出现）；「七彩跳变」预置改成 渐亮 4 / 亮 8 / 暗 8（老效果照旧读自己存的三段）；暂停样本帧停在包络顶点（有亮段停满亮第 0 拍，只有渐亮时停在爬满那一拍）。渲染端仍保留「`r + h + f` 比停留短 → 多出来的拍黑着」的夹紧兜底（老存档 / 手改 JSON）。

**测试**：`test_effects_core` 111 → 122（渐亮形状 `63/127/191/255` + 变暗不落 0 / 换色处没有黑帧 / 顶点 / 一拍照跳 / 夹紧 / 缺省 / 停留 = 渐亮 + 亮 + 暗 / 实例与渲染）、`test_effects_c_exec` 新增一条「渐亮跳变」模式随整帧真编译比对（第 1/6 拍 = 169/254，渐亮分支确实执行；变暗分支也在 37 帧逐字节比对里）、`test_fx_presets` 77 → 80（三行显隐 / 三段之和自动填 / 封顶状态栏 / 切回跳变仍等于三段之和 / 七彩跳变 rise 0 / 暂停样本帧停在爬满那一拍）；全量 **24 套件 / 1440 项 / 0 FAIL**。

**影响**：跳变仍每帧每分区一次包络计算（整数、无浮点、除法不在像素循环里）；导出结构体比上一版多 1 字节（共三列），固件侧只需用新导出的头文件覆盖。

## 2026-10-17 —— 跳变不再硬切：每种颜色「快速点亮 → 渐灭」再换下一个

**动机**（用户原话）：「现在的跳变太生硬了，我想要的是，在慢速的时候，快速呼吸的点亮，然后再渐灭切至下一颜色，如此循环多种颜色。快速的时候呢，就亮灭快一点，切换也快一点。」

**根因**：跳变只做了「每 N 拍换一个颜色」—— 整条从满亮直接跳到另一个满亮，停留 20 拍时就是每 400ms 一次硬切，边缘非常生硬。

**改动**：新增 `stepEnv(t, d)`（JS）与 `led_gen_step_env()`（生成的 C，逐值相同）：前 1/8 停留（至少 1 拍）0→255 快速点亮，剩下 `255→0` 匀速渐灭、最后一拍正好灭；`renderZoneMaskTo` / `led_gen_zone_render` 把包络乘进 `mask`（`(m × (env+1)) >> 8`，只乘亮度、不动颜色）。换色那一瞬灯已经黑到底 —— 这就是「不硬切」的全部秘密。停留越短，亮灭与切色一起变快；停留 1 拍仍是一拍一色（闪烁），老效果手感不变。编辑台暂停帧改停在包络顶点（`tick_cnt=0` 时包络为 0，否则整条全黑、像「没生效」）。

**测试**：`test_effects_core` +6（包络形状 / 顶点满亮 / 中途渐灭）、`test_effects_c_exec` +1（真编译的 C 也在渐灭：169/255）、`test_fx_presets` +1（暂停帧看得见）；全量 **24 套件 / 1390 项 / 0 FAIL**，C/JS 逐字节一致。

**影响**：跳变每帧多一次「每分区一次除法 + 每像素一次乘加」（除法不在像素循环里），与呼吸同一量级。

## 2026-10-17 —— 效果页：调色板跟着配色模式收口（纯色只剩 1 个可选色）

**动机**（用户原话）：「选择纯色模式时，调色板就只保留一个可选色就行了，其他的隐藏了。但是如果其他的色彩模式需要用到多种配色时，这个就还是要保留的。」

**根因**：`renderPalette()` 不分配色模式，把 `palette` 里 2~8 个色块全画出来 —— 纯色只用第 1 个，后面几个除了占地方还会误导（以为改它们会有变化）；`+` / `−` 也一直亮着，纯色 / 覆盖下点了没意义（覆盖只用前 2 个）。

**改动**：`led_layout_editor.html` —— ① 新增 `palFixed(color)`：纯色 1 / 覆盖 2 / 跳变·呼吸 0（个数由用户定）/ 其余 -1（不用调色板）；② `renderPalette()` 只画前 N 个，色数标签补「（另 K 个收起）」；③ 纯色那一行标题改成「颜色」，`+` / `−` 收起；覆盖只画 2 个、还差第 2 色时留一个 `+` 补齐；④ `palAddColor()` / `palDelColor()` 加同样的守卫，提示语说清「只用 N 个，不用再加 / 删不得」；⑤ **收起只影响显示**：`palette` 数据不动，切回跳变 / 呼吸原样回来。

**测试**：`test_fx_presets` 48 → 57（纯色只 1 个色块且存档里个数不变、标签写明收起几个、切回跳变全回来；覆盖只 2 个色块且加减收起；呼吸 3 色照旧全画）；全量 **24 套件 / 1383 项 / 0 FAIL**。

**影响**：纯界面层，预览取样与导出的 C 一字未改（`test_effects_c_exec` 仍逐字节一致）。

## 2026-10-17 —— 效果页：改配色 / 套预置后编辑台「立刻看得见」

**动机**（用户原话）：「修改配色方案，似乎没有立即生效。」

**根因**：三处都让编辑台画老快照 / 退化帧 —— ① `fxStruct()`（套预置 / 增删图层 / 开关效果）只 `afterChange()`，而 `stageSync(false)` 按效果 id 命中缓存，实例里还是旧配色；② `stageSync()` 用 `curEffect()` 建实例，微调绑定「覆盖参数」时画的是**库里那条原效果**（覆盖与它 id 相同，缓存也直接命中）；③ 编辑台默认**暂停**、永远停在 tick 0：呼吸 `breathGain(0)=0` 整条全黑，跳变 / 覆盖 = 调色板第 1 色、渐变相位 0（红），跟「纯色红」长得一模一样 —— 看着就像没生效。

**改动**：`led_layout_editor.html` —— ① `fxStruct()` 先 `stageRefresh()` 再 `afterChange()`（后者里的 `render()` 才把新帧画出去）；② `stageSync()` 改用 `editTarget()` 并给缓存键加 `eff:` / `bind:` 前缀 —— 微调绑定「覆盖参数」时编辑台画的一直是库里的原效果（两者 id 相同，缓存直接命中）；③ 新增 `stageSampleFrame(inst)`：暂停时把预览实例拨到「看得出区别」的一帧（呼吸 = 包络顶点、覆盖 = 盖到一半、跳变 = 第一个非黑颜色、渐变 = 相位 85 的绿）；④ `stageToggle()` 先落 `stagePlaying` 再 `stageSync()`，保证**按播放仍从 tick 0 开始**（样本帧只活在暂停预览里，不碰固件算法）；⑤ 配色提示补一句「第 N 层是空间色相，会盖过这里选的配色」。

**测试**：`test_fx_presets` 44 → 48（呼吸暂停不再是全黑、覆盖同屏两色、彩虹环 ≥6 种色相）、`test_override` + 5（微调时改调色板 → 预览立刻变蓝，且改动只落覆盖副本）；全量 **24 套件 / 1374 项 / 0 FAIL**。

**影响**：只改编辑台的预览取样与刷新时机，导出的 C / 预览的固件语义一字未改（`test_effects_c_exec` 仍逐字节一致）。

## 2026-10-17 —— 效果页配色内核：纯色 / 跳变 / 渐变 / 彩虹 / 呼吸 / 覆盖

**动机**（用户原话）：「色彩变换一般也就分几种：纯色、跳变色、渐变色、彩虹色……还有一种就是覆盖色」「算法尽量的简单高效，以契合固件，芯片性能有限」。

**根因**：效果级原来只有「单色 / 彩虹循环 / 渐变循环」三档 —— 其中「渐变循环」只是相位 +85 的双色彩虹（`c1/c2` 从没接线，颜色②是死控件）；「渐变」也不是红→黄→绿→青→蓝→紫。缺跳变 / 真彩虹 / 呼吸 / 覆盖。

**改动**：`led_layout_editor.html` —— `FW.COLOR` 扩到 0..6（2 留给老存档），新增 `COLOR_UI`；效果新增 `palette`（≤8 色）/ `levels` / `hue_base` / `hue_speed` / `period`，`normalizeEffect` 给老存档补字段；`colorUpdate` 实现跳变 / 呼吸的每帧换色，`renderZoneMaskTo` 加呼吸包络、覆盖的 `0xFE` 哨兵、彩虹的 q/r 递推（**像素循环里没有除法**）；`effectColorAt` / `effectPreset` / `modesPlan` / `led_gen_effect_t` / `led_gen_palette[]` / C 的 `led_gen_tick` + `led_gen_zone_render` 同步；UI 换成调色板色块 + 按模式显隐参数；预置新增「彩虹环 / 七彩跳变 / 多色呼吸 / 颜色覆盖」，帮助页与提示同步。

**测试**：`test_effects_core` 70→90、`test_effects_c_exec` 12→18（4 种新模式的 C/JS 逐字节比对）、`test_fx_presets` 32→44；全量 **24 套件 / 1365 项 / 0 FAIL**。

## 2026-10-15 —— 批 7-D-4：用户第四轮实测（点灯有偏差 / 形状手柄拖不动）—— 画布映射 + 「谁抢按下」的规则

- **动机**（用户实测两条）：「现在不单单是新建的形状没办法通过鼠标调节大小，**连点选某一个灯都有点偏差了**」。这两条看着无关，其实是同一个根：**屏幕上看到的东西**与**命中测试算出来的世界坐标**用的不是同一套映射，而「这一下算谁的」也没有明文规则。
- **① 根因：画布位图与「CSS 盒子 × dpr」会脱节**（真正的系统性偏移）。浏览器是把 `cv.width/height`（**位图**）**拉伸**到 CSS 盒子上显示的，而命中测试（`s2w`）按 **CSS px** 算 —— 位图一旦过期，整块画布就**按比例偏**、越靠边偏得越多（`test_canvas_map` 实测 CSS 盒子 1200→960 时偏 **212 世界 px**，远超一颗灯的命中半径）。而画布是 flex 子元素：右栏宽度、面板内容高低、滚动条有无、窗口在不同 DPI 的显示器之间移动、浏览器缩放导致 dpr 变化……**都不发 `window.resize`**，原来只挂了 `resize` 与右栏拖拽。现在三道保险：`render()` 开头 `if (canvasStale()) resizeCanvas()`（**任何一次重画都自愈**）、boot 时 `initCanvasWatch()` 给画布挂 `ResizeObserver`、`watchDpr()` 按当前 dpr 登记 `matchMedia('(resolution: Xdppx)')`、dpr 变了重算并**重新登记**。顺带 `resizeCanvas()` 在盒子还没布局出来（宽/高 < 1）时不再把位图设成 1×1。
- **② 命中半径改成「屏幕感知」**：`hitTol() = max(0.42 格, 9 屏幕 px)`（按当前缩放换算成世界 px）。老写法固定 0.42 格（世界 px），缩到 0.3 倍只剩 2~3 屏幕 px —— 等于要求用户按亚像素精度点灯；命中取的仍是**最近的一颗**（不是第一颗），所以放宽不会把点击判给旁边的灯。
- **③ 「谁抢按下」写成了明文规则**（同一个歧义的两个方向，正是用户抱怨的两条）：
  - **手柄任何模式抓住都算改大小**：新增 `handleAnyAt()`（当前形状优先）+ `beginShapeDrag()` —— 一次按住就直接开拖（先 `enterShapeEdit()` 再立刻开 `resize` draft），不再「先点中形状、松手、再按第二遍」。以前**选择模式按在手柄上只是进编辑态**，手感就是「拖不动」。
  - **手柄外那一圈（1.6 倍容差，`shHandleRing()`）也算改大小**，而且必须排在「包围盒内 = 挪动」**之前**：瞄着角上那个小方块按下去差几像素，原来要么整块形状连灯一起被挪走（还会重铺该区），要么掉出包围盒被当成「点空白」直接**退出编辑态**（手柄瞬间消失）—— 两条都最气人。
  - **只有画出来的东西才允许抢点击**：新增 `shapePicked` —— 选过某个形状之后，它的 8 个手柄在**选择模式下也一直画着**（看得见、抓得住）；别的形状那时不画手柄，也就不能抢。选择模式按住形状内部 = 选中它并**立刻能挪**（原来只是进编辑态，还得再按一次）。
  - **点灯不再被偷**：双击**落在灯点上**不再进形状编辑态（`dblclick` 里 `if (hit(wx, wy)) return;`）—— 原来连点两颗灯会悄悄把工具换成形状编辑态，之后每次点灯都在挪形状，看着就是「点灯有偏差」。进编辑态的明确入口三条：面板「形状」下拉、新增的「**编辑**」按钮 `#shEdit`、画布上双击形状里的**空白处**。
  - **顺手修掉两处状态机漏洞**：`pointercancel` 现在会收干净（`shDraft` / `drag` 不再挂着）；「还没真拖过」的 draft 不算一笔操作（Esc 不会只吃掉一个空 draft 而忘了释放编辑态，也不会误触 `undo()`）。
  - **「看不见的手柄不许存在」**（画与抢必须同源）：`setMode()` 现在**当场 `render()`**（原来切模式不重画，会留下一屏过期的手柄 —— 看得见却抓不住，正是这一轮抱怨的同类坑；boot 早期 `state` 还没装就跳过）；手柄只在**编辑态 / 选择模式 + `shapePicked`** 时画，放置 / 擦除模式一个都不画；删掉形状后 `shapePicked = false`（选择模式不替「下一个」形状画手柄）。
- **测试**：新增 **`tests/test_canvas_map.mjs`**（32 项）—— 把浏览器的**位图 / CSS 盒子 / dpr** 三样分开建模，再用记录型 2D 上下文抓住 `render()` 真正用的变换与每一次 `arc`，于是「屏幕上那个灯点被点下去会选中谁」是**算出来**的：基线点 #0/#36/#103 都选中自己；CSS 盒子变了先量出「不重算会偏 212 px」再验 `ResizeObserver` 一到就重算；只来一次 `render` 也能自愈；dpr 1→1.5 重算并重新登记；选择模式抓手柄一次手势改大小；手柄外一圈仍算改大小；**切到放置 / 擦除模式后同一帧里那 8 个手柄小方块不再出现**（切回选择模式又回来）；末段把上面每条硬规矩都写成源码正则断言。`test_ui` 196 → **209**：17.10 改成新语义（双击灯点**不**换模式 / 双击形状空白才进编辑态 / 「编辑」按钮进得去），新增 17.13（选择模式抓手柄一次手势改大小）、17.14（缩到 0.26 倍、点偏 0.44 格仍选中那一颗；偏过中点就选更近的那颗）。**测试驾具本身也修掉一处会误导人的东西**：`test_ui` 的「世界 → 客户端」映射原先是「拖个框反推 zoom」，反推起点带半格误差 —— 现在直接取 `render()` 最后一帧的变换（`ctxM()`，精确）；17b 的空白校准点也改成**算出来一定空白**的点（原来的试错拖拽会落进已有形状里、把工程本身改掉：一挪形状就重铺该区，104 颗灯变 103 颗、编号整体挪位）。全量 **23 套件 / 984 项 / 0 FAIL**。**导出物与契约零改动**（形状 / 坐标不进固件）。
